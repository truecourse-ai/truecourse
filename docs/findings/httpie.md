# HTTPie — documentation & behavior findings

**Target:** [httpie/cli](https://github.com/httpie/cli), v3.2.4 (editable install from source at commit `5b604c3`, last committed 2024-12-17) — driven through the real CLI (`.venv/bin/http`, installed by the recipe's `python3 -m venv .venv && pip install -e .`) in a clean, **offline** sandbox, 2026-07-17.
**Method:** TrueCourse guard generated executable test scenarios from HTTPie's single-file manual (`docs/README.md`, 2601 lines / 151 sections) and ran them against the current code. Because the sandbox has no network, every scenario the pipeline could author uses HTTPie's `--offline` mode, which *builds and prints* the request without sending it. Each finding below was re-verified by hand against the live CLI before being listed; findings the pipeline attributed to its own test-generation mistakes are excluded from the table.
**Tracker cross-check:** the verified finding and the two target bugs (#1642, #1640) were searched against HTTPie's GitHub issues and PRs (open and closed) on 2026-07-17.

## Summary

**One real documentation-vs-code drift, and it is a clean one.** The guard run surfaced 37 findings for human review. Hand-verification against the live CLI classified them as **1 genuine doc drift, 1 environment-only (offline-unreachable) claim, and 35 test-generation defects** — every one of the 35 was a scenario that under-tested or mis-encoded its claim while the tool behaved exactly as documented. The single real drift: HTTPie's manual says Boolean JSON values are **"not allowed"** with `--form`, but the tool silently accepts them.

The honest headline on scope: **HTTPie is a client whose whole purpose is talking to servers, so most of its manual is not observable offline.** The 49 committed scenarios (all 49 pass) cover the part that is — the request *builder* (`--offline` output), auth-header construction, config resolution, and syntax/parse errors. Everything requiring a real HTTP round-trip (~89 sections), an install (~21), or that is pure prose (~22) fell into coverage gaps. Contrary to expectation, **none** of the 37 findings came from a scenario that tried to hit the network — the pipeline correctly wrapped everything in `--offline`. The real environment casualties were 51 scenario-authoring calls that hit tool-side usage throttling (blank `claude exited 1`) and produced no scenario this run.

Tracker classification: **the real finding is unreported (1 related-history PR); both target bugs are out of this offline run's reach.**

## Findings

| # | Finding | Evidence | Tracker status |
|---|---------|----------|----------------|
| 1 | **`--form` accepts Boolean JSON values, which the manual says are "not allowed."** `docs/README.md` line 698 states: *"You can switch your request to `--form` or `--multipart`, and string, float, and number values will continue to be serialized … Other JSON types, however, are not allowed with `--form` or `--multipart`."* The section's own preceding example (line 665) labels `married:=false` as *"Raw JSON — Boolean"* — i.e. one of the disallowed "other" types. But the shipped tool accepts it. | `http --form --offline --ignore-stdin example.org married:=false` → exit **0**, body `married=False`. Arrays (`hobbies:=[…]`), objects (`favorite:={…}`), and `null` are correctly rejected (exit 1, *"Cannot use complex JSON value types with --form/--multipart."*) — **only Booleans slip through.** Root cause: `httpie/cli/requestitems.py:181` gates on `isinstance(output, (str, int, float))`, and in Python `bool` is a subclass of `int`, so `False`/`True` pass and are serialized with `str()` — yielding the Python-repr string `married=False` (capital-F, not JSON `false`). | **Unreported.** No issue reports Booleans being accepted under `--form`. **Related history:** #1213 (MERGED, *"Proper JSON handling for `:=`/`:=@`"*, fixes #1212) introduced this `--form` primitive-passthrough; the doc was written to exclude Booleans, the code's `isinstance(int)` check never did. |

This is a documentation-vs-code drift, not a crash: the behavior looks intentional at the code level (a "primitives are fine, complex types error" model) but disagrees with the manual's narrower "string, float, and number only" wording, and the Python-repr serialization (`False`, not `false`) is a plausible latent bug of its own.

## The pipeline's 37 review findings, verified

Guard raised 37 findings for human triage. They fall into two mechanical groups, and hand-verification against the live CLI confirmed the tool behaves as documented in **every** case except finding 1:

**24 "fidelity" findings — the scenario under-tests its claim (generation defect).** These are the pipeline's own review flagging that a generated scenario checks a substring but not the whole claim: e.g. the empty-password scenario asserts a base64 prefix that would still match a *non-empty* password; the JSON-default-headers scenarios check one of three asserted headers; the "interface-design" form-POST scenarios check one header instead of the full raw request. In each the tool is not in question — the scenario is simply too weak. Not tool or doc bugs.

**13 birth-failures — a scenario ran and its assertion failed. All 13 verified live; 11 are generation defects, 1 is real (finding 1), 1 is environment-only.** The two dominant defect patterns, both artifacts of the guard harness running the CLI with a **non-interactive stdin that the scenario forgot to `--ignore-stdin`**, and with **piped (non-tty) output**:

- *Missing `--ignore-stdin` flips the request.* With stdin present and not ignored, HTTPie reads it as a body — turning an intended `GET` into a `POST`, enabling JSON mode, or raising *"Request body … and request data … cannot be mixed."* This sank the "default request headers" scenario (got `Accept: application/json…` instead of `Accept: */*`), the "unset `Accept:`" baseline step, the `Content-Length:` unset scenario, and the `--raw` scenario. Re-run *with* `--ignore-stdin`, the docs are exactly right: `http --offline --ignore-stdin example.org` yields `GET`, `Accept: */*`, `Accept-Encoding: gzip, deflate`, `User-Agent: HTTPie/…`, `Host: example.org`; and `Accept:` correctly removes the default Accept header.
- *Piped output is compact `\r\n` raw HTTP, but the regex assumed pretty-printed `\n`.* The nested-JSON, top-level-array, escaped-index, and explicit-index scenarios all asserted multi-line, key-ordered pretty JSON. Live, the *structure* is exactly as documented (`[]:=1 []:=2 []:=3` → `[1, 2, 3]`; `object[\1]=…` → string key `"1"`; `search[keywords][1]=APIs [0]=CLI` → `["CLI", "APIs"]`) — only the formatting/ordering assertion was wrong (HTTPie disables prettification when stdout is not a terminal). One scenario (`introduction.5`) even hard-coded a typo (`"CLIs"`/`"API"`).
- *Type-safety* (`type-safety.2`) delivered its key-vs-index conflict via an input pack that never became CLI request-items, so no conflict was built and stderr was empty; supplied directly (`x[a]=1 x[0]=2`), HTTPie raises the documented `HTTPie Type Error: Cannot perform 'index' based access on 'x' …` (exit 1).

**The one environment-only finding: `other-notes.1` (Accept-Encoding + `--download`).** The manual (line 2056) says *"`Accept-Encoding` can't be set with `--download`."* The scenario ran `--offline --download example.org Accept-Encoding:gzip` and saw `gzip` survive. But this is not a drift: the identity-encoding override lives in `httpie/downloads.py:193` (`request_headers['Accept-Encoding'] = 'identity'`), a **send-time** hook (`Downloader.pre_request`) that `--offline` never reaches — offline builds the request but never downloads. Confirmed: `--offline --download` leaves Accept-Encoding at the default `gzip, deflate` regardless. The doc is accurate for real downloads; the claim is simply **not observable in an offline sandbox**, which is exactly the environment bucket.

**Auto-resolutions (2).** The run also auto-resolved 2 scenarios without human review, both `fidelity-discard`: the `--ciphers` help scenario (checks the flag name appears in `--help`, not the default cipher string) and the header-from-file `:@` scenario (a `contains` check that would pass even without newline-stripping). The `:@` behavior itself verifies correct live — `X-Data:@file` reads `secret-token\n` and sends `X-Data: secret-token`, newline stripped.

## The offline-sandbox reality

HTTPie's core job — send a request, show the response — cannot be exercised without a server, and this sandbox has none. That shapes everything:

- **What's testable offline (and got covered):** the request **builder**. `--offline` prints the exact bytes HTTPie would send, so anything about request *construction* is checkable: JSON/nested-JSON/array body building, form & multipart encoding, auth headers (`-a`, bearer), default headers, header setting/unsetting, cookies, compression flags, config-file resolution, and every syntax/parse error and `--help`/`--version` path.
- **The 49 committed scenarios** (all pass in `guard/LATEST.json`) cover exactly this surface: 11 JSON body-construction, 9 forms/file-upload, 6 config, 5 authentication, 5 http-method, 5 http-headers, 3 compressed-request-body, 2 cookies, and one each of chunked-transfer-encoding, offline-mode, and SSL-ciphers-via-help.
- **What's not testable offline (154 coverage gaps):** ~89 sections describe a real network round-trip or response handling (status codes, redirects/`--follow`, streaming/download, sessions against a live host); ~21 are installation instructions (Homebrew, apt, pip, Snap, standalone binaries — all network/package-manager); ~22 are prose/intro/meta with no CLI-assertable claim (feature lists, credits, license, "about the docs"); the rest are blocked on other executables (`https`, `httpie-manager-cli`) or an interactive TTY (the password prompt).

So roughly **a third of the manual's sections yield an offline-observable claim** (49 scenarios), and about two-thirds require a server, an install, or state no behavior at all. This is not a gap in the tool or the pipeline — it is what a network client's manual looks like when you unplug the network.

**Run economics (worth stating honestly):** the run made 263 LLM calls for ~$65.69 and was truncated by throttling — 51 authoring calls failed with a blank `claude exited 1` (the usage-limit signature), leaving ~35 sections unsettled. Those sections got no scenario this run; a re-run resumes from the cached successes.

## Notes on interpretation

- **The signal-to-noise here is the story.** 37 findings, 1 real. But the 35 defects are not the pipeline hallucinating tool bugs — 34 are the pipeline's *own* review correctly flagging weak or mis-encoded scenarios (fidelity discards + `\r\n`/tty/`--ignore-stdin` mismatches), and every one, verified live, confirms the tool matches its docs. The triage did its job; hand-verification overturned none of it.
- **The `--ignore-stdin` and non-tty-formatting patterns are a harness lesson, not a tool bug.** A CLI that changes its request based on whether stdin is a terminal (curl-like) needs scenarios authored with `--ignore-stdin` and with tty-independent assertions. The generated scenarios often omitted these, producing failures that look like drift but aren't. This is the most actionable feedback for the generator on network-client targets.
- **The one real finding is a good upstream candidate.** It is a precise, reproducible doc-vs-code disagreement (`README.md:698` vs `requestitems.py:181`) with a clean root cause and a plausible latent serialization bug (`False` vs `false`). It would fit either a one-line doc fix or a one-line code fix depending on intended behavior.
- **Maintenance state.** v3.2.4, last commit 2024-12-17; repo active. The drift is old — it predates the current head and no one has filed it, consistent with a claim that only bites users who mix `--form` with Boolean `:=` values.
