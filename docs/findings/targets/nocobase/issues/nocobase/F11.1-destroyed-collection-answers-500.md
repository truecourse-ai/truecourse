# A data request to a destroyed collection answers 500 TypeError, where the same API answers 404 for a collection that never existed

## * Describe the bug

After a collection is removed with `collections:destroy`, a data request against its name does not answer `404`. It answers `500` with a JavaScript type error:

```
GET /api/tcdestroy:list
-> 500 {"errors":[{"message":"Cannot read properties of undefined (reading 'collection')"}]}
```

The destroy itself is correct. The table really is gone from PostgreSQL. What is wrong is the answer the API gives afterwards: a caller that reads a collection which has since been dropped gets an internal error instead of "this resource is not here", and any client that distinguishes 4xx from 5xx will treat a normal, expected condition as a server fault, retry it, and page someone.

#### The control, which is the argument

This is not a claim about what `404` *should* mean here. It is what this very API already answers for the only other way a collection can be absent:

```
GET /api/tcneverexisted:list
-> 404 Not Found
```

Same endpoint, same shape of question, two different answers. A name that never existed is a clean `404`. A name that existed until a moment ago is a `500` type error. The product already has the right answer for an absent collection; the destroyed case simply does not reach it.

#### Cause

The resourcer route outlives the collection, so the request is dispatched normally and the action runs with no repository behind it.

`packages/core/actions/src/utils.ts:26-39`, `getRepositoryFromParams(ctx)` ends at

```ts
return ctx.db.getRepository<Repository>(resourceName);
```

which is `undefined` once the collection is gone. There is no undefined guard on the way out.

`packages/core/actions/src/actions/list.ts:37`:

```ts
let { simplePaginate } = repository.collection?.options || {};
```

https://github.com/nocobase/nocobase/blob/032a4f6913be912f57462d605cbd0bde97b599c6/packages/core/actions/src/actions/list.ts#L37

The optional chain sits one level too deep. It guards `.options`, but `repository` itself is the undefined value, so reading `.collection` off it throws `TypeError: Cannot read properties of undefined (reading 'collection')`. The live server's own stack agrees: the throw is inside `listWithPagination` at `.../actions/list.js:66:46`.

## * How To Reproduce

Everything below is verbatim from one run on an instance built from the commit above. All values are the real ones from that run.

**1. Create a collection, give it a field, and put a row in it.** As the super admin:

```
POST /api/collections:create
{"name":"tcdestroy","title":"TC Destroy","template":"general"}
-> 200

POST /api/collections/tcdestroy/fields:create
{"name":"label","type":"string","interface":"input"}
-> 200

POST /api/tcdestroy:create
{"label":"row one"}
-> 200 {"data":{"id":1,"label":"row one"}}
```

**2. Confirm the collection reads normally before the destroy.** This is what makes the later 500 a change of behaviour rather than a broken fixture:

```
GET /api/tcdestroy:list
-> 200 {"data":[{"id":1,"label":"row one"}],"meta":{"count":1,"page":1,"pageSize":20,"totalPage":1}}
```

**3. Destroy it.**

```
POST /api/collections:destroy?filterByTk=tcdestroy
-> 200 {"data":1}
```

The destroy is correct and complete. Read straight from PostgreSQL:

```
select count(*) from information_schema.tables where table_name='tcdestroy';
-> 0
```

**4. Read the destroyed collection. This is the bug.**

```
GET /api/tcdestroy:list
-> 500 {"errors":[{"message":"Cannot read properties of undefined (reading 'collection')"}]}
```

**5. The control, a name that never existed at all.** Nothing was created under this name at any point in the session:

```
GET /api/tcneverexisted:list
-> 404 Not Found
```

## Expected behavior

`GET /api/tcdestroy:list` after the destroy should answer `404`, the same as `GET /api/tcneverexisted:list`, since from the caller's point of view both describe a collection that is not there.

Two ways to get there, in preference order:

1. **Fix it at the source.** Have `getRepositoryFromParams` (`packages/core/actions/src/utils.ts:26-39`) throw a 404 when the named resource has no repository. That is one place, and it covers every action that goes through it rather than just `list`. We drove only `list` in this report, so we are not claiming the other actions are broken in the same way, but they take the same helper and are worth checking in the same change.

2. **Or at least stop the type error.** Guard `repository` in `listWithPagination` before dereferencing it, so the failure is an error the API chose rather than a crash. This removes the 500 but leaves each action to answer for itself.

Either way the caller should be able to tell a missing resource from a server fault, which today it cannot.
