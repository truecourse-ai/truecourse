# fields:create with a field interface and no data type answers 500 unsupported field type null, where the manual says the interface carries a default

## * Describe the bug

Creating a field through the API with a field interface and no data type answers a `500` carrying a JavaScript error message:

```
POST /api/collections/<collection>/fields:create
{"name":"amount","interface":"number"}

-> 500 {"errors":[{"message":"unsupported field type null"}]}
```

Two things are wrong at once, and they stack neatly.

**First, the default the manual describes is not applied.** `docs/docs/en/data-sources/data-modeling/collection-fields/index.md:64`:

> Each Field interface has a default data type. For example, a field with the Number interface uses `double` by default, but it can also use `float`, `decimal`, and other data types.

That default is applied by the browser form, not by the field. A caller going through the API has to supply `type` by hand, and the value it has to supply is exactly the `double` the manual says is the default.

**Second, and independently, a bad request is answered as a server fault.** Even if `type` is deliberately required at the API, `500 unsupported field type null` is the wrong answer for a request the server understood well enough to know what was missing. A `400` naming the missing field is what belongs there.

#### The control, which is the argument

The identical request, with the one field the caller had to guess:

```
POST /api/collections/<collection>/fields:create
{"name":"amount2","type":"double","interface":"number"}

-> 200 {"data":{"key":"53xebcq5fbl","name":"amount2","type":"double","interface":"number",
        "collectionName":"9tcbad","description":null,"parentKey":null,"reverseKey":null}}
```

Same endpoint, same session, same collection, same interface. The only difference is the `type` key, and the value that makes it work is the default the manual publishes. So this is not a broken endpoint or a broken collection: it is a documented default that exists in one client and not in the API, and an untyped error where a validation error belongs.

#### Cause

`packages/core/database/src/database.ts:777-780`:

```ts
const Field = this.fieldTypes.get(type);

if (!Field) {
  throw Error(`unsupported field type ${type}`);
}
```

https://github.com/nocobase/nocobase/blob/032a4f6913be912f57462d605cbd0bde97b599c6/packages/core/database/src/database.ts#L777-L780

`type` arrives as `null` because nothing between the request and here fills it in from `interface`. The throw is a bare `Error` rather than a typed application error, so the koa error handler has no status to work with and renders it `500`. That single choice is what turns a missing-field validation into a server fault.

## * How To Reproduce

Both requests below are verbatim from one run on an instance built from the commit above, as the super admin, against the same collection and one after the other.

A note on the collection name, so it does not distract: ours was called `9tcbad`, a leftover from an unrelated probe earlier in the same session. Any collection reproduces this. Substitute your own name.

**1. The probe, an interface with no type.**

```
POST /api/collections/9tcbad/fields:create
  Content-Type: application/json
  {"name":"amount","interface":"number"}

-> 500 {"errors":[{"message":"unsupported field type null"}]}
```

**2. The control, the identical request with the type the manual calls the default.**

```
POST /api/collections/9tcbad/fields:create
  Content-Type: application/json
  {"name":"amount2","type":"double","interface":"number"}

-> 200 {"data":{"key":"53xebcq5fbl","name":"amount2","type":"double","interface":"number",
        "collectionName":"9tcbad","description":null,"parentKey":null,"reverseKey":null}}
```

**3. Compare with the manual.** `docs/docs/en/data-sources/data-modeling/collection-fields/index.md:64` says the Number interface uses `double` by default. Step 2 is a caller supplying that default by hand because step 1 will not.

## Expected behavior

Taking the two halves in the order a maintainer can act on them:

1. **Answer `400`, not `500`.** Whatever is decided about defaults, a `fields:create` that cannot be satisfied should be refused with a `400` naming what is missing, for example "field type is required when no default is available for interface `number`". Today it raises a bare `Error` at `database.ts:779` and koa renders that as a server fault, which tells a client to retry rather than to fix its request. This is the smaller change and the one that is clearly right either way.

2. **Or apply the documented default at the API.** If the interface-to-type default is meant to be part of the product rather than of the browser form, resolve it server side in `fields:create` so `{"name":"amount","interface":"number"}` creates a `double` field, exactly as the manual describes.

If neither is wanted, then the manual sentence quoted above should say that the default is a property of the interface picker in the UI and that `type` is required when creating fields through the API. Any of the three is a coherent position. The current state, where the manual promises a default and the API answers a 500 with a JavaScript message, is not.
