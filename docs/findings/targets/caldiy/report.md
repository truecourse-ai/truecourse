## Cal.diy (calcom/cal.diy, the community fork; v2 bookings and slots API, public booking pages)

> This is the Cal.diy section of a review that covered three products in one pass. The shared scoreboard, the verdict vocabulary and the method notes are in [../README.md](../README.md).

**Context that shapes everything here.** Cal.diy is the MIT fork of Cal.com created in spring 2026 "with all enterprise/commercial code removed" (its README). The public `calcom/cal.com` repository now mirrors `calcom/cal.diy` (same `main` commit `176037d0af`, identical tree, verified 2026-08-15); the commercial source is private. The docs the scenarios were generated from (`cal.com/docs`, `cal.com/help`) describe the commercial, hosted product. So beyond the usual verdicts this target has **edition mismatch**: the doc claim is true of Cal.com and simply not part of Cal.diy. Those are not defects, but they are still information a Cal.diy maintainer does not have written down anywhere: the fork ships its own `docs/api-reference/v2/openapi.json` saying `2024-08-13`, while every public page says `2026-02-25`.

**Thirteen real defects, three doc bugs, thirty edition mismatches, thirty-four noise.** Of the 16 findings, 15 have no upstream report; one (the phone prefill) is issue calcom/cal.diy#29739 and was fixed on `main` by PR #29740 on 2026-08-05, five days after the tested commit, in no tag. Only 4 commits landed on `calcom/cal.diy` `main` between the tested commit and 2026-08-08, so "not fixed after" is nearly automatic; for the commercial Cal.com nothing is verifiable from source.

### Edition mismatches (30): the docs describe Cal.com, not the fork

- **23 API scenarios: the documented `cal-api-version` does not exist in Cal.diy.** Every public reference page for bookings mandates `2026-02-25` (`BookingsController_2026_02_25_*`, "Must be set to 2026-02-25"), list pagination mandates `2026-05-01`; the tested tree's `packages/platform/constants/api.ts:56-68` tops out at `2024-09-04`, and `apps/api/v2/src/bootstrap.ts:31-41` **silently downgrades any unknown version to `2024-04-15`**, whose flat DTO wants `timeZone`/`language`/`metadata` and whitelist-strips the documented `attendee` object. Result: a 400 naming three fields the caller never sent, or (on GET) a 200 in the wrong shape. 28 of the 29 scenarios carrying a 2026 header failed. Public trace: issue calcom/cal.diy#28762 (open, names "from 2024-08-13 to 2026-02-25 for POST /bookings ... break silently"), #29785 (open, newer-date fallback), #28512 (closed, same downgrade ignoring a filter); PR #28561 (map 2026-02-25 to 2024-08-13) closed unmerged 2026-03-25, its author confirming prod serves 2026-02-25 while the source tree does not. The fork's own `docs/api-reference/v2/openapi.json` correctly says `2024-08-13`. Two follow-ups a maintainer would want: the silent downgrade should be a 400 naming supported versions (a Cal.diy-side defect independent of the edition), and a re-run pinned to `2024-08-13` is what would actually test these 23 flows, most of whose bodies are accepted verbatim there (a sibling scenario proves it).
- **7 scenarios: the documented feature was removed by the fork or never ported.** Booking email verification endpoints (`/v2/bookings/verification/*` do not exist; only `/v2/atoms/verification/*`, and one unauthenticated GET to `api.cal.com` confirms the documented path is live on the hosted product); user-level booking limits (two scenarios; no `bookingLimits` on `User`, only `EventType` and `Team`; issue #8985 open since 2023, PRs #14243/#23100/#25641 unmerged; docs from calcom/help#115); team-inside-organization slots (`organizationSlug` branch deleted by the fork commit, the param survives in the DTOs and is silently ignored); `POST .../request-reschedule` (unrouted at every version; PR #28243 closed unmerged); `rescheduleWithSameHost` (round-robin engine removed; the event-type toggle `rescheduleWithSameRoundRobinHost` survives as a live UI switch and Prisma column that nothing reads, a silent no-op worth filing); SMS-reminder phone requirement (Workflows removed, the `smsReminderNumber` field injection deleted, the v2 hook that looks for it is permanently dead). Also, instant meetings and routing forms are gone (`CreateInstantBookingInput` deleted, `handleInstantMeeting` absent; routing tables dropped by migration), found underneath two of the version-header failures.

### Noise, honestly (34)

- **26 test defects.** Twelve are one pattern: the generator hardcodes a slot label ("9:00am", "10:00") on `reference-host`, the single seeded host, and a sibling scenario in the same parallel run booked that slot first; Cal.diy correctly counts an ACCEPTED booking as host-wide busy time (`BookingRepository.ts:686-795`, no `eventTypeId` filter; buffers widen it, so a 30/30-buffered booking removes three slots), so the label vanishes and the walk dies before any milestone. The rest are assertions the doc never made (a literal "has not been confirmed", the `value` attribute of a `<textarea>`, `^https?://` on an ICS `data:` URI, optional `rescheduledFromUid` keys, a top-level `bookingFieldsResponses` on the seated shape, `role: listitem` with a name for a role that takes no name from content, day buttons behind a modal that aria-hides them, an unauthenticated visit to `/bookings/upcoming`, mark-absent on a future booking, an invalid phone number `+19876543210`, an hourly grid on a 30-minute event type). Researcher #3 lands here: the 9:10 override yielding one 9:30 slot is the documented default slot grid (`slots.ts:68`, Optimized Slots off; calcom/cal.diy#25011 closed as intended).
- **8 environment.** Seven are the first-wave saturation (17 web scenarios started at once against a just-started `next start`, Prisma `connection_limit=3`, 10 s step budget including `page.goto`; first-wave navigations median 13 s, later 4 s; screenshots after the deadline show the correct rendered page). One is a recipe issue: `NEXT_PUBLIC_WEBAPP_URL` is baked at build to `http://localhost:3000`, the app ran on another port, and a reschedule redirect left the app under test (landing on TrueCourse's own dashboard).
