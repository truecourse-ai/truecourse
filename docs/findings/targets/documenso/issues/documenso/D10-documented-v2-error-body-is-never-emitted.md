# The v2 error format published on first-api-call.mdx ({error, code, statusCode}) is not what the API returns

## Issue Description

`apps/docs/content/docs/developers/getting-started/first-api-call.mdx` publishes an "Error Response Format" block and three worked "Common Errors" examples in the shape `{ "error": ..., "code": ..., "statusCode": ... }`. No tRPC-backed v2 endpoint emits `error` or `statusCode`. The real body is the tRPC/OpenAPI shape `{ message, code, data: { code, httpStatus, path, appError } }` (plus `issues` on a Zod validation failure). An integrator who writes an error handler from the getting-started page reads `err.error` and `err.statusCode`, gets `undefined` for both, and their error messages disappear.

This is now the last page in the repo carrying that shape. PR #3133, merged 2026-08-19 and in v2.17.0, replaced the identical block on `rate-limits.mdx` with the real `{ message, code, data: { code, httpStatus, appError } }`, so the correction has already been accepted here; it simply did not reach the getting-started page. Neither #3137, #3138 nor #3139 touches this block either (I read #3137's `first-api-call.mdx` hunks: they change the 429 row at L441 and the rate-limit prose at L485 and step over L447-L484).

One thing to keep the wording honest, because a flat "the v2 API never returns `error`" would be wrong: the hand-rolled Hono download routes mounted at the same `/api/v2` prefix (`apps/remix/server/api/download/download.ts:129-141`, mounted at `apps/remix/server/router.ts:127`) really do return `{ error, code }`, and `packages/app-tests/e2e/api/v2/partial-signed-pdf-download.spec.ts` asserts against that second family. So `/api/v2` serves two error envelopes by design, and the correct statement is that the generated (trpc-to-openapi) routes, which is everything the getting-started page walks the reader through, never emit `error` or `statusCode`.

There is a second, smaller half of this that is a product matter rather than a docs one, described under Cause: on AppError-derived failures the top-level `code` reads `INTERNAL_SERVER_ERROR` even when the HTTP status is a correct 404, so the code taxonomy in `common-errors.mdx` is unusable at the top level and callers have to dig into `data.code`.

https://docs.documenso.com/docs/developers/getting-started/first-api-call, section "Error Handling" (`apps/docs/content/docs/developers/getting-started/first-api-call.mdx`, lines 447-484 at today's head, https://github.com/documenso/documenso/blob/75330166cc00b29c14399bc2e391e4b4d8080c00/apps/docs/content/docs/developers/getting-started/first-api-call.mdx#L447-L484):

The page's other two pages of the same docs set already publish the real shape, for example `recipients.mdx`: "Example Error Response: `{"message": "Recipient already exists"}`".

### Cause

The doc block is hand-written and describes an envelope the tRPC surface cannot produce. Every v2 endpoint generated by trpc-to-openapi returns the tRPC error shape: `packages/trpc/server/trpc.ts:39-67` (https://github.com/documenso/documenso/blob/3cf2963cd03d8b24770b7490bdb20e596baa5d65/packages/trpc/server/trpc.ts#L39-L67) builds the body from tRPC's default shape `{message, code, data}` and only enriches `data` (with `appError`, `code`, `httpStatus`) when the cause is an `AppError`. `apps/remix/server/trpc/hono-trpc-open-api.ts:21-33` separately forces the HTTP status to the AppError's mapped status, which is why the status line is a correct 404 while the body keys are the tRPC ones. There is no `error` member and no `statusCode` member on that path. On a Zod input failure the message is rewritten by trpc-to-openapi to the literal "Input validation failed" with the detail in `issues`.

The block was written by PR #2460 "feat: docs v2" (`b92c53dbb2`, 2026-02-27); `git blame` on lines 440-485 is 100 percent that one commit. It has never matched the implementation. The code it misdescribes is older and unrelated.

Product half, the `INTERNAL_SERVER_ERROR` rider: `genericErrorCodeToTrpcErrorCodeMap` in `packages/lib/errors/app-error.ts:70-111` already carries the correct TRPCError code for each app error code, but both of its call sites read `?.status` and never `?.code` (`packages/trpc/server/trpc.ts:59` and `apps/remix/server/trpc/hono-trpc-open-api.ts:27`). The `code` half of that table is dead, so an AppError-derived 404 comes out labelled `INTERNAL_SERVER_ERROR` at the top level with `NOT_FOUND` one level down. Note this does not affect errors thrown as real `TRPCError`s: a Zod input failure correctly reads `BAD_REQUEST` at the top level, as the second reproduction below shows.

Still present at today's head. `git log 3cf2963cd0..origin/main` on `packages/trpc/server/trpc.ts` is empty, so the errorFormatter is byte-identical: https://github.com/documenso/documenso/blob/75330166cc00b29c14399bc2e391e4b4d8080c00/packages/trpc/server/trpc.ts#L39-L67 . `app-error.ts` took two commits since the tested tag (#3159, #3229) which only add three `AppErrorCode` members and two map rows, and the map's `code` half is still read by nobody.

Suggested doc fix for `first-api-call.mdx`: replace the Error Response Format block and the three Common Errors examples with the real body, state that the HTTP status is on the status line and mirrored at `data.httpStatus`, and say that the application error code lives at `data.code` / `data.appError.code` rather than at the top level. The replacement text that landed on `rate-limits.mdx` in #3133 is the right model. It is also worth noting that a missing recipient email never yields the human-readable "Recipient email is required" string, so that example needs rewriting on its content and not only on its shape.

Suggested product fix, if the maintainers would rather make the docs true: construct the TRPCError with `genericErrorCodeToTrpcErrorCodeMap[...].code`, which is already computed and discarded, so the top-level code stops reading `INTERNAL_SERVER_ERROR` on a 404.

## Steps to Reproduce

Tested on tag `v2.16.0` (`3cf2963cd03d8b24770b7490bdb20e596baa5d65`), built and run from source (`npm ci`, `npx turbo run build --filter=@documenso/remix`, `npm run start -w @documenso/remix`) against Postgres 17.

1. Ask for an envelope that does not exist, using the page's own "Envelope not found" case:

```
GET /api/v2/envelope/envelope_tcrefmissing00
Authorization: <token>
```

HTTP 404. The body has no `error` and no `statusCode`; the top-level `code` reads `INTERNAL_SERVER_ERROR`:

```json
{"message":"Envelope could not be found","code":"INTERNAL_SERVER_ERROR","data":{"code":"NOT_FOUND","httpStatus":404,"path":"envelope.get","appError":{"code":"NOT_FOUND","message":"Envelope could not be found"}}}
```

The server log confirms a clean `NOT_FOUND` AppError, no 500 and no stack trace: `{"status":"error","appError":{"code":"NOT_FOUND","message":"Envelope could not be found"},"path":"envelope.get","msg":"TRPC_ERROR_HANDLER"}`.

2. Now the page's "Missing required field" case, a create whose one recipient has no email:

```
POST /api/v2/envelope/create
Authorization: <token>
Content-Type: multipart/form-data; boundary=tcguard

--tcguard
Content-Disposition: form-data; name="payload"

{"type":"DOCUMENT","title":"tcref-createbad2","recipients":[{"name":"TCRef No Email","role":"SIGNER"}]}
--tcguard--
```

HTTP 400. Again no `error` and no `statusCode`, and the message is the generic validation string rather than "Recipient email is required":

```json
{"message":"Input validation failed","code":"BAD_REQUEST","data":{"code":"BAD_REQUEST","httpStatus":400,"path":"envelope.create"},"issues":[{"code":"invalid_union","unionErrors":[...],"path":["payload","recipients",0,"email"],"message":"Invalid input"}]}
```

Re-tested live on v2.17.0 (75330166cc, 2026-08-19): still reproduces. 404, 400 and 401 bodies were captured; none carries a top-level error or statusCode, the AppError-derived 404 and 401 both carry top-level code INTERNAL_SERVER_ERROR, the zod 400 correctly carries BAD_REQUEST, and the 401 shows statusCode does exist, nested at data.appError.statusCode.

## Expected Behavior

The Error Handling section of `first-api-call.mdx` prints the body the generated v2 endpoints actually return, so an error handler written from the page works. Concretely, for the 404 case:

```json
{
  "message": "Envelope could not be found",
  "code": "INTERNAL_SERVER_ERROR",
  "data": {
    "code": "NOT_FOUND",
    "httpStatus": 404,
    "path": "envelope.get",
    "appError": { "code": "NOT_FOUND", "message": "Envelope could not be found" }
  }
}
```

with a sentence saying that the HTTP status is on the status line and mirrored at `data.httpStatus`, and that the application error code is at `data.code`. Better still, the product stops labelling AppError-derived failures `INTERNAL_SERVER_ERROR` at the top level, in which case the documented top-level `code` becomes usable and matches `common-errors.mdx`.

## Current Behavior

The published shape and the emitted shape share only the key `code`, and even that carries a different value than the page's taxonomy implies. `error` and `statusCode` do not exist on any generated v2 response, so `err.error` and `err.statusCode` are `undefined` for every caller who follows the page.
