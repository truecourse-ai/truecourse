## 1. TriliumNext/Trilium — search is the broken subsystem

### Product bugs (confirmed)

**T1 · The fuzzy operators `~=` / `~*` never lex (F7).**
A query using the documented fuzzy operators returns unranked substring
results; the operator never reaches the parser as a token. Scenario:
`fuzzy-search-tolerates-a-typo.api.1` (step 9). Upstream: issue **#9426 open**,
PR **#9508** (direct fix) and PR **#10633** (search overhaul) both open,
unmerged.

**T2 · An unrecognised note property degrades to matching the whole tree (F8).**
`not(note.ancestor.title = …)` (or any expression naming a property the parser
does not know) silently answers with every note including `root` and
`_hidden` — a wrong-but-plausible result set with no error. Scenario:
`boolean-expressions-group-and-negate-a-search.api.1` (24). Upstream: **#5432
open**, but it only reports `noteSize`; the degradation behaviour itself is
unreported.

**T3 · DB-backed search properties are order-dependent; `revisionCount` is dead
(F9, corrected).** The recorded claim ("`note.contentsize` never matches") is
the right symptom with the wrong mechanism. Verified reality, which is worse:
any query whose trimmed text **starts with `#`** short-circuits past the code
path that loads sizes into the in-memory cache — so on a cold server
`#label note.contentSize >= 0` answers `[]` while the reordered
`note.contentSize > 0 AND #label` answers the note, **and running the second
query permanently fixes the first for the life of the process** (the loader
memoises onto becca). Identical queries answer differently depending on search
history. `revisionCount` is separately and unconditionally dead on both paths.
Scenario: `note-properties-are-searchable.api.1` (16). Upstream: #5432 covers a
sliver; the order-dependence and `revisionCount` are unreported.

**T4 · Multi-word `=` is a substring compare (F10).** An exact-match phrase
also matches longer strings that merely contain it. Scenario:
`the-exact-match-operator-in-quick-search.api.1` (16). Upstream: **#9422
open**; PR #10633 closes it.

**T5 · The lexer strips commas even inside quotes (F6).** The documented
geolocation idiom `#geolocation="48.8583,2.2945"` is unmatchable by search;
a comma-free quoted value matches fine. Scenario:
`a-geo-map-marks-the-children-that-carry-a-geolocation.web.1` (7).
**Unreported.**

**T6 · A saved search never executes itself, and "Search now" is broken (F13).**
Opening a saved-search note renders "Search has not been executed yet." —
and the DOM control sharpened it: clicking the offered **Search now** button
navigates to a *different* note id with an empty query and returns the whole
instance (23 results) instead of the saved query's 2. Scenario:
`a-search-backed-collection-shows-notes-from-across-the-tree.web.1` (17).
Upstream: **#5658 open, filed as a feature request**; the broken button is
unreported.

**T7 · `clone-to-branch` 500s on an empty body (F11).** A `PUT` with no body
throws a TypeError destructure and answers 500; `{"prefix": null}` works.
No board red (found while authoring). **Unreported.**

**T8 · Creating any typed note without `content` 500s (F12, broadened).**
Recorded against `book` notes; verified to be type-independent —
`{"title":"x","type":"text"}` 500s identically. The title defaults when
missing; content throws a bare `Error`. **Unreported.**

**T9 · Note titles are never HTML-sanitised (F17).** Both creation-with-title
and `PUT /title` store `<b>bold</b> <script>x</script> plain` verbatim. The
control is the sharp part: a `#titleTemplate`-derived title comes back
sanitised — `sanitizeHtml` works and is wired up, but it sits on the one branch
a user-typed title never reaches. **Unreported.**

## 2. rybbit-io/rybbit — one false "fixed", two timing bugs

### Product bugs (confirmed)

**R1 · Site creation never invalidates `sitesAccessCache` (F5) — and upstream
closed it as fixed.** Create a site, then immediately create a goal/funnel or
read its exclusion config: **403 "no access"** for up to ~15 s (the cache TTL);
the identical request succeeds after 16 s. Ten board scenarios red on it.
Verification also found structure the corpus could not see: the cache has two
independently-keyed halves (`${userId}:false` for goals/funnels/exclusion
reads, `${userId}:true` for `PUT /config`), and `requireSiteAdminAccess`
exempts better-auth **system admins** before the cache — the first user in a
fresh DB is auto-promoted, so an owner-seeded corpus can never 403 on the
config PUT; a second non-admin account proved that half (403 → 200 after 16 s).
Upstream: **#980, closed "completed" 2026-05-22 with "Will be fixed in the next
version!" — confirmed NOT fixed at this SHA.** The invalidation call exists and
is called from member-management paths, never from site creation. Scenarios
(step 2): `a-custom-event-goal-counts-only-its-own-event.api.1`,
`a-goal-follows-the-dashboards-range-and-filters.api.1`,
`a-goal-narrowed-by-an-event-property.api.1`,
`a-page-goal-counts-the-sessions-that-reached-its-path.api.1`,
`a-page-goal-pattern-matches-one-segment-or-many.api.1`,
`an-incomplete-goal-is-refused.api.1`,
`six-goal-types-and-six-funnel-step-types.api.1`,
`a-funnel-refuses-fewer-than-two-steps.api.1`; (step 3, on the exclusion GET):
`an-excluded-path-is-accepted-but-never-stored.api.1`,
`ip-exclusions-in-every-supported-format.api.1`.

**R2 · Whole-second timestamps + strict ordering break funnels and entry/exit
pages (F6).** Two funnel-step events landing in the same wall-clock second
never advance the funnel (strict `>` on a 1 s-resolution timestamp): step 1
counts the session, step 2 reads 0, the completer lands in "Dropped Off".
The same tie makes a two-page visit's exit page read as its entry page.
Control: the same events spaced >1 s apart behave correctly. Six scenarios:
`a-two-step-funnel-reports-its-conversion-and-its-dropoff.api.1` (10),
`a-custom-event-funnel-step-matches-by-name.api.1` (7),
`a-funnel-step-can-be-labelled-and-narrowed.api.1` (8),
`the-sessions-behind-a-funnel-step.api.1` (8),
`entry-and-exit-pages-of-a-two-page-visit.api.1` (7),
`a-goal-card-and-the-sessions-that-converted-it.web.1` (8). **Unreported.**

**R3 · A "Today" window hides events stamped in the current second (F11) —
deterministic, not a flake.** The date-range upper bound is a strict `<`
against whole-second `now()`, so a just-flushed event is visible to the
realtime surface but invisible to every date-range surface until the next
second. The corpus measured it as a ~5% board flake; verification parked the
write just after a second boundary and reproduced it **7 of 8 rounds with gaps
up to 934 ms** — a real dashboard opening at the wrong moment renders "No
sessions found" while realtime shows the visitor. No stable board red (it roams
across the four web date-range readers). **Unreported.** Two one-line upstream
fixes would close it.

**R4 · `/api/track` acknowledges before the event is queryable (F10).**
Measured at random phase: 30–972 ms gap, median 555 ms, 12/12 immediate reads
empty. Undocumented consistency window; it is why seven corpus scenarios need
polled preconditions. **Unreported.**

**R5 · The Pages tab drops untitled pageviews (F8).** A pageview with no
`page_title` appears in the paths listing and is absent from the titles
listing the Pages tab renders. No board red (the seed supplies titles).
**Unreported.**

### Doc drift (confirmed, doc-side)

- **R6 (F7)** — docs name channels `Search`/`Social`; stored values are
  `Organic Search`/`Organic Social`, so filtering by the documented name
  matches nothing. `a-filter-narrows-the-whole-dashboard.api.1` (7).
- **R7** — the Sessions list has no "Bounce" status though the docs describe
  one. `the-session-list-has-no-bounce-status.web.1` (7).
- **R8** — a query-param exclusion blocks with a kind absent from the doc's
  evaluation list (which also omits ASN). `an-undocumented-exclusion-kind-still-blocks.api.1` (3).
- **R9** — journeys are pageviews-only though `journeys.mdx` says a node is a
  page OR an event. `journeys-render-the-paths-visitors-walk.api.1` (11).
- **R10** — a lowercase country code is refused 400, not normalised as
  promised. `country-exclusion-cannot-reach-a-private-address.api.1` (5).

All unreported.

## 3. nocobase/nocobase — ACL enforcement by silence

### Product bugs (confirmed) — all unreported upstream

**N1 · Field-level Edit permission silently discards ungranted fields (F13) —
the sharpest finding of the wave.** A role whose Edit grant covers `[alpha]`
sends an update naming `alpha` and `beta`: the response is **200**, `alpha`
changes, `beta` is silently dropped, no error anywhere. Mechanism: the grant's
`fields` list becomes a repository **whitelist** — it filters, never refuses
(`acl.ts:120-131`). Control: a role with no update grant at all does get a 403,
so the silence is specific to partial grants. Scenario:
`field-permissions-decide-which-fields-a-role-may-read-and-write.api.1` (17).

**N2 · `X-Role: __union__` is silently rewritten to another role.** Under the
default role mode, a caller asking for the union of their roles is not refused
(as any other unheld role name is, 401 `ROLE_NOT_FOUND_FOR_USER`) — the
middleware substitutes `userRoles[0]` and the request runs as a different role.
The control removes all doubt: the answer is byte-identical to naming
`userRoles[0]` explicitly, and flipping the mode to `allow-use-union` turns the
same header into a genuinely different (larger) result. Scenario:
`roles-are-used-one-at-a-time-under-independent-roles.api.1` (6).

**N3 · Identifier validation is browser-only (F10).** `collections:create`
accepts a collection named `9tcbad…` and `fields:create` accepts `9bad`; the
rule the manual states lives in a client-side `x-validator: 'uid'` with no API
equivalent. Scenarios: `a-collection-name-is-chosen-once-and-then-fixed.api.1`
(2), `a-field-identifier-is-validated-once-and-then-fixed.api.1` (7).

**N4 · `fields:create` with an interface and no type answers 500 (F11.2).**
`{"name":"amount","interface":"number"}` → `500 unsupported field type null`.
The interface's default data type is applied by the client form; the API
neither applies it nor rejects cleanly. Scenario:
`a-field-interface-carries-a-default-data-type-and-allows-others.api.1` (3).

**N5 · A data request to a destroyed collection answers 500 where 404 belongs
(F11.1).** Clean control pair from verification: a collection that never
existed → `404 Not Found`; the destroyed one → `500 Cannot read properties of
undefined (reading 'collection')` (the guard sits one level too deep,
`actions/list.ts:37`). Scenario:
`collections-are-listed-filtered-and-deleted-with-their-tables.api.1` (10).

**N6 · An `own`-scope over a collection with no `createdById` is an opaque 403
(F12 product half).** The union read answers `403 No permissions` with the real
reason (`createdById field not found`) discarded; adding the column flips the
same request to 200. Scenario:
`role-union-merges-the-rows-either-role-may-see.api.1` (6) — a SEED-class red
on the board, but the product half is real.

**N7 · `install` outside a live server is an unawaited race (S1) — PARTIAL.**
The unawaited `mainApp.runAsCLI(…)` is exactly where recorded
(`gateway/index.ts:706-724`), so the race exists in source — but it did not
fire in 15 cold installs, idle or under 8-way CPU contention. One trap
verified for future readers: `aiEmployees`/`aiSkills` tables fill on *first
boot*, not install, so a fresh install can look truncated and isn't.

**N8 · `install -f` drop-then-refuse (S2) — NOT REPRODUCED.** Six runs,
including one against the corpus's exact pre-state: `install -f` dropped and
fully reinstalled every time. The corpus's recorded S2 symptoms are what S1's
race would produce on the longer forced path — S2 is most likely S1 wearing a
different hat, and should not be filed as an independent bug.

## 4. AmruthPillai/Reactive-Resume — a dead metric and a validation class

### Product bugs (confirmed) — all unreported upstream

**RR1 · The `downloads` statistic has no write path (F3) — headline, now
end-to-end.** An anonymous visitor opens the public page, presses
`Download PDF`, and **verifiably receives the file** (a real Playwright
`download` event for `resume.pdf`) — while `downloads` stays `0` and
`lastDownloadedAt` stays `null`, with `views`/`lastViewedAt` moving beside them
as the control. Nothing in the repository ever passes `downloads: true`
(regression from the v5.1.0 client-side PDF rewrite). Scenario:
`the-downloads-metric-counts-a-visitors-pdf.web.1` (6).

**RR2 · Silent `.catch()` coercion is a class, not a field (F9, broadened).**
The corpus recorded `metadata.template` (`.catch("onyx")` rewrites an
out-of-enum template on a 200). Verification drove every bound the aborted
scenario never reached: `page.format = "a3"` → 200, stored `a4`;
`page.marginX = 500` → 200, stored `14`; `typography.body.fontSize = 999` →
200, stored `11`. **Thirty `.catch()` sites** in the schema; the 11 bounds
without one all correctly 400. Any API client that sends an out-of-range value
gets a 200 and different data. Scenario:
`the-resume-document-refuses-values-outside-the-documented-bounds.api.1` (3).

**RR3 · Form controls with no accessible name (F7).** `FormControl` stamps its
id on the render-prop's root — a `<fieldset>` (`Slug`), a `<div>` (`Tags`), a
`div[role=group]` (the Sidebar Width slider) — none labelable, so
`getByLabel` finds nothing and the real control has no name. Verification
corrections: 2 of the 15 builder spinbuttons are anonymous (not all 15), and
3 of the 5 cited call sites are actually correct; a **second defect family**
surfaced instead — `FormLabel`s pointing at ids no element carries
(`Picture → Size`, `Basics → Website`) and a duplicate DOM id from two
`FormControl`s in one `FormItem`. Scenarios:
`create-a-resume-from-the-dashboard.web.1` (6),
`find-the-space-settings-the-guide-points-at.web.1` (13),
`rename-a-resume-from-the-resume-menu.web.1` (12). Nearest upstream artefact
#2844 (open) concerns the rendered resume, a different surface.

**RR4 · The dashboard's `Sort by` and `Filter by` comboboxes have no
accessible name (F8).** Decorative labels with no `htmlFor` /
`aria-label` / `aria-labelledby`; a combobox takes no name from its contents,
so neither list control is addressable by name. Scenarios:
`filter-the-dashboard-by-a-tag.web.1` (7),
`sort-the-dashboard-from-the-sort-menu.web.1` (5).

**RR5 · Views are deduped per client per hour (F4).** Two loads by the same
visitor inside an hour count 1 (`WINDOW_MS = 60*60*1000`); a distinct client
increments. A product decision, but the docs promise "counted each time
someone loads" — so it lands as drift with a mechanism. Scenario:
`a-public-visit-is-counted-in-the-statistics.web.1` (11).

**RR6 · The `@version` directive is advisory (F10).** Omitting it is a warning
(`Valid with warnings`) and the stylesheet applies — proved byte-for-byte:
the versionless PDF renders identical to the `@version 1;` PDF, and the
genuinely-fatal `@version 2;` PDF renders identical to no stylesheet. Doc says
to keep `@version 1;` at the start of every stylesheet. No board red.

### Doc drift (confirmed, doc-side) — all unreported

- **RR7 (D2)** — format buttons never "show a spinner and stay disabled": the

- **RR8 (D8)** — "type a password … and confirm": one field, no Confirm.

- **RR9 (D13)** — "press Cmd/Ctrl+Z to undo the restore": the undo stack is

- **RR10 (D14, PARTIAL → sharper)** — a template switch is an ordinary
  throttled autosave, not a snapshot moment: on a virgin resume it does write
  one row (labelled `Manual save`, never naming a template), and further
  switches inside the 2-minute throttle write nothing. Both halves of the
  guide's sentence are wrong. `a-template-switch-takes-a-snapshot.web.1` (15).
- **RR11 (D24)** — docs spell `Free-Form`; the app renders `Free-form`.
  `change-the-page-format.web.1` (14).
- **RR12 (D25)** — the Template section shows one preview; the gallery the
  template images live in is omitted by the guide.
  `switch-the-resume-template-from-the-gallery.web.1` (16).
- **RR13 (D26/D27)** — no `Hidden` switch exists and clicking a section
  heading opens nothing; the real path (Section options → Columns) works.
  `hide-a-section-and-lay-it-out-in-two-columns.web.1` (14).
