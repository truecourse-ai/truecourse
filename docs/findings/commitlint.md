# commitlint — documentation & configuration findings

**Target:** [conventional-changelog/commitlint](https://github.com/conventional-changelog/commitlint), version 21.2.1 (commit `336be92`, cloned and built from source, 2026-07-17)
**Method:** TrueCourse guard (v0.7.3-next.8) generated executable test scenarios from commitlint's own documentation — the per-package READMEs under `@commitlint/*` and the reference/API docs under `docs/` — and ran them against the current CLI (`node @commitlint/cli/cli.js`) in a clean sandbox after a full `pnpm install` + `pnpm build`. Every finding below was then re-verified by hand against the live CLI before being listed. Scenarios the automated review attributed to its own test-generation shortfalls are excluded.
**Tracker cross-check:** every finding was searched against commitlint's GitHub issues and PRs (open and closed) on 2026-07-17.

## Summary

2 verified divergences in commitlint's documentation. One is a documentation-vs-behavior bug: a shareable config's README shows example output the code no longer produces. The other is an internal contradiction: two documents give opposite install commands for the same package. Of the 74 executable scenarios generated from the documentation and committed, **all 74 pass** against the current code — commitlint's documented CLI behavior is otherwise accurate.

Tracker classification: **0 exact, 1 related, 1 unreported.**

## Findings

### Documentation vs. behavior

| # | Finding | Tracker status |
|---|---------|----------------|
| 1 | **`@commitlint/config-pnpm-scopes` README example omits the always-present `global` scope.** `@commitlint/config-pnpm-scopes/readme.md` (Examples, line 35) shows `test(foo)` failing with `scope must be one of [api, app, web] [scope-enum]`. The code unconditionally appends a `global` scope (`index.ts` line 71: `scopes.add("global")`), so with the README's own `api`/`app`/`web` workspace the real output is `scope must be one of [api, app, global, web] [scope-enum]`. Reproduced in a hermetic workspace seeded with only `api`, `app`, `web` (no stray `global` package). | **Related.** PR #4553 ("feat(config-pnpm-scopes): allow global scope", merged 2025-09-29) added `global` to the code and its tests but did not update the README example, which still shows the pre-feature list. Open issue #3658 asks how to add scopes beyond workspace names. No issue or PR reports the stale example. |

### Documentation vs. documentation

| # | Finding | Tracker status |
|---|---------|----------------|
| 2 | **The same package is documented with two opposite install flags.** `@commitlint/load/README.md` (line 8) says `npm install --save-dev @commitlint/load`; `docs/api/load.md` (line 8) says `npm install --save @commitlint/load`. Same package, contradictory flag. The repo-wide convention is `--save-dev` for commitlint packages (34 of 47 install lines), which the package README follows; the `docs/api/*` copies for the importable library packages (`load`, `read`, `lint`, `format`, `parse`) use `--save`. | **Unreported.** No issue or PR addresses this inconsistency. (Doc-install fixes exist for other setup snippets — e.g. #4490 for the husky command — but none for load's flag.) |

## Notes on interpretation

- **Finding 1 is a stale example, not a code bug.** The `global` scope was added deliberately (PR #4553); the README's Examples block was simply never updated to match. A user copying the README's `api`/`app`/`web` setup and running the README's own `test(foo)` command sees `global` in the allowed list, which the documented output does not mention.
- **Finding 2 is a genuine contradiction with a defensible either-side.** Treating `@commitlint/load` as dev tooling argues for `--save-dev` (the package README, and the repo's dominant convention); treating it as a library you import at runtime argues for `--save` (the API doc). It is listed because the two documents disagree, not because one flag is provably wrong. The same README-vs-`docs/api` split recurs for the sibling library packages `read`, `lint`, `format`, and `parse`.
- **All 74 committed scenarios pass.** They cover the documented CLI-observable behavior across the config-conventional / config-angular rules (subject-case, type-case, type-enum, header/body/footer max-length, empty subject/type, leading-blank), the `--strict` exit-code contract (2 for warnings, 3 for errors), config auto-discovery (`.commitlintrc.json`/`.yml`, `commitlint.config.mjs`, the `package.json` field), `--default-config`, `--extends` precedence, rule levels (0/1/2) and the `always`/`never` inversion, array/function/async-function rule notations, local plugins, and the workspace-scope and pnpm-scope configs.
- **19 generated candidates were set aside as test-generation shortfalls, not defects.** Most under-tested a two-sided claim — e.g. asserting that a valid scope or an allowed type is accepted without ever feeding the case that should be rejected, so the check would stay green even if the rule were disabled. A hand-sample of six confirmed every one: in each, the code and documentation agree, and a committed sibling scenario exercises the half the weak candidate omitted (for example, the discarded "type-enum accepts every documented type" is backed by committed scenarios that reject `foo`, and the discarded workspace-scope "accepts a matching scope" is backed by committed scenarios that reject a non-workspace scope). Two candidates crashed on a generated config shim (a bare-directory ESM import) instead of testing anything, and one npm-published-plugin scenario could not resolve its plugin inside the hermetic sandbox (Node's ESM resolver ignores the seeded path) — both are sandbox artifacts, not divergences; the documented *local*-plugin path is exercised by committed, passing scenarios. None buried a real problem.
- **107 documentation sections state no CLI-checkable behavior** and are legitimately outside a CLI test's scope: package taglines and install/setup snippets with no stated outcome (81 sections), API-only examples that require importing a package as a library (23), one interactive commit-prompt flow, and two behaviors gated on an external environment (a Node 24+ config-loading note and the Travis CI wrapper).
- **The scenarios are bounded by what the docs state as CLI-checkable behavior.** Four known code bugs in this project are **not** covered by the generated scenarios: #4620 (`subject-case` rejects non-Latin/Cyrillic lowercase subjects), #4640 (type detection breaks when a `!` is combined with custom issue prefixes), #4656 (a line is parsed as a body without a preceding blank line), and #4704 (`--git-log-args=--first-parent` silently ignored since v20). The docs document the surrounding features — `subject-case`, `subject-exclamation-mark`, custom `issuePrefixes`, and the `--git-log-args` flag all appear, and where CLI-observable they are exercised by passing scenarios — but none states the specific broken behavior as a concrete, assertable example. #4704's flag even survives the `--help` scenario because the help text still lists it; the runtime regression needs a multi-commit git history to observe. These are real bugs outside what the documentation pins, not gaps the scenarios failed to catch.
