# Strapi, Documenso and Cal.diy: what the guard found, reviewed failure by failure (August 2026)

Three SaaS products were run through the guard pipeline (spec scan of the product's own published docs, scenario generation, guard run against a live instance) on 2026-08-13 and 2026-08-14. Every failing scenario was then reviewed one at a time: read the evidence bundle, find the doc sentence, root-cause it in the tested source, git-blame the culprit, search the upstream tracker (issues and PRs, open and closed), and check whether a later commit on the upstream default branch fixes it. This document is the result. It exists to answer one question with evidence a maintainer can check: does pointing this pipeline at a real product surface real, novel, actionable defects, or noise?

Verdict vocabulary used throughout: **real defect** (the product does not do what its docs or its own schema say, and a user following the docs is harmed), **doc bug** (the product is sane and intentional, the doc text is wrong), **test defect** (the generated scenario asserted something the doc does not promise), **environment** (the sandbox, not the product or the test).

What the numbers say: **34 of the 37 Strapi and Documenso failures reviewed are the product's or the docs' fault, 3 are noise.** Of the 34, 28 had no upstream report at all; 6 had been independently noticed by one Documenso community contributor whose docs PRs sit unmerged; exactly one has an upstream fix, which landed 52 minutes after the release we tested. Every one of the researcher's 16 itemized findings (8 Strapi, 8 Documenso) was confirmed at source level; the review refined most of them (narrower or wider scope, a deeper root cause, a corrected "unreported" claim). Beyond those 16, the review surfaced 12 more distinct real defects and doc bugs the write-up did not have.

## Cal.diy (in progress)

The Cal.diy run (`calcom/cal.diy` `main` @ `038381aeca`, 101 scenarios, 77 fail + 3 error) is under the same per-failure review; this section is filled in as results land. Two facts already established shape it:

- **The public `calcom/cal.com` repository is now a mirror of `calcom/cal.diy`** (same `main` commit `176037d0af`, identical tree, verified 2026-08-15). The commercial Cal.com source is private. The docs the scenarios were generated from (`cal.com/docs`, `cal.com/help`) describe the commercial product, so a Cal.diy failure can be an **edition mismatch**: a documented feature, field or API version (for example `cal-api-version: 2026-02-25` with `allowBookingOutOfBounds`, which Cal.diy silently downgrades to 2024-04-15) that Cal.diy does not ship. Those are recorded as such, with the public trace (issue calcom/cal.diy#28762 names that exact drift), not as defects.
- **The Cal.diy sandbox was saturated at run start**: about 16 concurrent browser scenarios against one `next start` with `connection_limit=3` and a 10 s step budget. Booking pages that omit `?month=` pay two sequential slot fetches and were still painting skeleton cells at the deadline (screenshots seconds later show the fully rendered, correct page). A run of early web failures are this, and are recorded as environment, with the harness fix named (pin `?month=`, warm one booking page after the health check, raise the connection limit above the worker count).

The researcher's five Cal.diy items (`docs/guard-findings.md` in that repo) are being cross-checked the same way; the first divergence is already in: their #3 (a 9:10-10:10 override yields one 9:30 slot) is Cal.com's documented default slot grid (`slots.ts:68`, Optimized Slots off), with maintainers declining to change it in calcom/cal.diy#25011.

## Method and limits

- Verdicts come from the evidence bundle (request, response, transcript, screenshots, server logs), the bound doc page, and reading the tested source; not from a live re-run. Where evidence did not settle it, the reviewer said so rather than guessing.
- "Fixed after" was checked against the upstream default branch fetched 2026-08-15 (`strapi/strapi` `develop` @ `acf0ce2034`, `documenso/documenso` `main` @ `688ef2fdf3`, `calcom/cal.diy` `main` @ `176037d0af`) and against tags.
- Tracker searches were bounded (three per failure); "none found" means those searches, with the queries recorded in the per-failure result files.
- The per-failure JSON results (verdict, quotes, file:line, blame, tracker items, queries) are the source for every row above.
