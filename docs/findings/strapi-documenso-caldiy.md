# Strapi, Documenso and Cal.diy: what the guard found, reviewed failure by failure (August 2026)

Three SaaS products were run through the guard pipeline (spec scan of the product's own published docs, scenario generation, guard run against a live instance) on 2026-08-13 and 2026-08-14. Every failing scenario was then reviewed one at a time: read the evidence bundle, find the doc sentence, root-cause it in the tested source, git-blame the culprit, search the upstream tracker (issues and PRs, open and closed), and check whether a later commit on the upstream default branch fixes it. This document is the result. It exists to answer one question with evidence a maintainer can check: does pointing this pipeline at a real product surface real, novel, actionable defects, or noise?

Verdict vocabulary used throughout: **real defect** (the product does not do what its docs or its own schema say, and a user following the docs is harmed), **doc bug** (the product is sane and intentional, the doc text is wrong), **test defect** (the generated scenario asserted something the doc does not promise), **environment** (the sandbox, not the product or the test).

"Distinct" counts one defect once even when several scenarios hit it (Strapi's two "Delete document" label scenarios are one doc bug) and counts the extra defects a single long scenario exposed (Strapi's relation scenario shows three). The scenario tables below list every failure.

What the numbers say. Strapi and Documenso: **31 of the 37 failures reviewed are the product's or the docs' fault, 6 are noise.** They collapse to 33 distinct findings (19 real defects, 14 doc bugs); 26 had no upstream report at all, 6 had been independently noticed by one Documenso community contributor whose docs PRs sit unmerged, and exactly one has an upstream fix, which landed 52 minutes after the release we tested. Cal.diy is a different picture and an honest one: **16 of 80 failures are product or doc findings (13 defects, 3 doc bugs, 15 of them unreported, one fixed upstream 5 days after the tested build), 30 are the docs describing the commercial product rather than the open-source fork, and 34 are noise from the run itself** (a saturated sandbox and a generator that hardcodes slot times on one shared host). Every one of the researcher's 16 itemized Strapi and Documenso findings was confirmed at source level; of their 5 Cal.com items, 4 were confirmed (two with narrower scope) and 1 was refuted (documented default behavior, maintainers declined to change it). Beyond the write-ups, the review surfaced 14 more distinct real defects and doc bugs on Strapi and Documenso, and 12 more on Cal.diy. Across the three products: 49 findings (32 real defects, 17 doc bugs), 41 with no upstream report, 2 fixed after the build we tested.

## Cal.diy (calcom/cal.diy, the community fork; v2 bookings and slots API, public booking pages)

**Context that shapes everything here.** Cal.diy is the MIT fork of Cal.com created in spring 2026 "with all enterprise/commercial code removed" (its README). The public `calcom/cal.com` repository now mirrors `calcom/cal.diy` (same `main` commit `176037d0af`, identical tree, verified 2026-08-15); the commercial source is private. The docs the scenarios were generated from (`cal.com/docs`, `cal.com/help`) describe the commercial, hosted product. So beyond the usual verdicts this target has **edition mismatch**: the doc claim is true of Cal.com and simply not part of Cal.diy. Those are not defects, but they are still information a Cal.diy maintainer does not have written down anywhere: the fork ships its own `docs/api-reference/v2/openapi.json` saying `2024-08-13`, while every public page says `2026-02-25`.

**Thirteen real defects, three doc bugs, thirty edition mismatches, thirty-four noise.** Of the 16 findings, 15 have no upstream report; one (the phone prefill) is issue calcom/cal.diy#29739 and was fixed on `main` by PR #29740 on 2026-08-05, five days after the tested commit, in no tag. Only 4 commits landed on `calcom/cal.diy` `main` between the tested commit and 2026-08-08, so "not fixed after" is nearly automatic; for the commercial Cal.com nothing is verifiable from source.

### Edition mismatches (30): the docs describe Cal.com, not the fork

- **23 API scenarios: the documented `cal-api-version` does not exist in Cal.diy.** Every public reference page for bookings mandates `2026-02-25` (`BookingsController_2026_02_25_*`, "Must be set to 2026-02-25"), list pagination mandates `2026-05-01`; the tested tree's `packages/platform/constants/api.ts:56-68` tops out at `2024-09-04`, and `apps/api/v2/src/bootstrap.ts:31-41` **silently downgrades any unknown version to `2024-04-15`**, whose flat DTO wants `timeZone`/`language`/`metadata` and whitelist-strips the documented `attendee` object. Result: a 400 naming three fields the caller never sent, or (on GET) a 200 in the wrong shape. 28 of the 29 scenarios carrying a 2026 header failed. Public trace: issue calcom/cal.diy#28762 (open, names "from 2024-08-13 to 2026-02-25 for POST /bookings ... break silently"), #29785 (open, newer-date fallback), #28512 (closed, same downgrade ignoring a filter); PR #28561 (map 2026-02-25 to 2024-08-13) closed unmerged 2026-03-25, its author confirming prod serves 2026-02-25 while the source tree does not. The fork's own `docs/api-reference/v2/openapi.json` correctly says `2024-08-13`. Two follow-ups a maintainer would want: the silent downgrade should be a 400 naming supported versions (a Cal.diy-side defect independent of the edition), and a re-run pinned to `2024-08-13` is what would actually test these 23 flows, most of whose bodies are accepted verbatim there (a sibling scenario proves it).
- **7 scenarios: the documented feature was removed by the fork or never ported.** Booking email verification endpoints (`/v2/bookings/verification/*` do not exist; only `/v2/atoms/verification/*`, and one unauthenticated GET to `api.cal.com` confirms the documented path is live on the hosted product); user-level booking limits (two scenarios; no `bookingLimits` on `User`, only `EventType` and `Team`; issue #8985 open since 2023, PRs #14243/#23100/#25641 unmerged; docs from calcom/help#115); team-inside-organization slots (`organizationSlug` branch deleted by the fork commit, the param survives in the DTOs and is silently ignored); `POST .../request-reschedule` (unrouted at every version; PR #28243 closed unmerged); `rescheduleWithSameHost` (round-robin engine removed; the event-type toggle `rescheduleWithSameRoundRobinHost` survives as a live UI switch and Prisma column that nothing reads, a silent no-op worth filing); SMS-reminder phone requirement (Workflows removed, the `smsReminderNumber` field injection deleted, the v2 hook that looks for it is permanently dead). Also, instant meetings and routing forms are gone (`CreateInstantBookingInput` deleted, `handleInstantMeeting` absent; routing tables dropped by migration), found underneath two of the version-header failures.

### Noise, honestly (34)

- **26 test defects.** Twelve are one pattern: the generator hardcodes a slot label ("9:00am", "10:00") on `reference-host`, the single seeded host, and a sibling scenario in the same parallel run booked that slot first; Cal.diy correctly counts an ACCEPTED booking as host-wide busy time (`BookingRepository.ts:686-795`, no `eventTypeId` filter; buffers widen it, so a 30/30-buffered booking removes three slots), so the label vanishes and the walk dies before any milestone. ## Method and limits

- Verdicts come from the evidence bundle (request, response, transcript, screenshots, server logs), the bound doc page, and reading the tested source; not from a live re-run. Where evidence did not settle it, the reviewer said so rather than guessing.
- "Fixed after" was checked against the upstream default branch fetched 2026-08-15 (`strapi/strapi` `develop` @ `acf0ce2034`, `documenso/documenso` `main` @ `688ef2fdf3`, `calcom/cal.diy` `main` @ `176037d0af`) and against tags.
- Tracker searches were bounded (three per failure); "none found" means those searches, with the queries recorded in the per-failure result files.
- The per-failure JSON results (verdict, quotes, file:line, blame, tracker items, queries) are the source for every row above; they are kept next to this file under `docs/findings/strapi-documenso-caldiy/<repo>/<scenario-id>.json`, with the review brief the reviewers worked from as `REVIEW-BRIEF.md` in the same folder.
