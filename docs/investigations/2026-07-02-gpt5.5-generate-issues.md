## Problem 1 & 2 — enumerate timeouts

`gpt-5.5` (via the proxy) is slow. The two biggest areas' enumerate calls exceeded the **300s enumerate ceiling** and were killed (`claude timed out after 300000ms` in the `.jsonl`). Those two areas (`core/endpoints`, `core/orders-entity`) therefore listed **no targets** → generated **no contracts**.

- Timeout constant: `spawnEnumerateRunner` in `packages/contract-extractor/src/corpus-generate.ts` (`timeoutMs = 300_000`). Its own comment already notes gpt-5.5 enumerate runs 140–180s+; here it blew past 300s.
- The area is NOT cached on a failed view (by design — so a re-run retries), which is why the CLI told the user to re-run.

**Directions:** make the enumerate/repair timeout model-aware or env-configurable; or note gpt-5.5 is unsupported for large areas. Claude (Opus/Sonnet) tiers are far faster and don't hit this.

## Problem 3 — loyalty_tiers repair-parse timeout (recovered)

One `contract.repairParse:Entity:loyalty_tiers` call hit the **600s repair ceiling** (`spawnGenerateRunner`/repair `timeoutMs = 600_000`). A subsequent retry succeeded, so `loyalty_tiers` was ultimately produced. Same slow-model root cause.

## Problem 5 — `FieldExposure:api-version-exposure` dropped (the interesting one)

**What happened.** The enumerate step classified "the API version, surfaced in service metadata and response headers" as a `FieldExposure` target. The extract call (`00019`) then produced:

```
field-exposure api-version-exposure {
  origin "docs/PRDs/orders_PRDv2.md" "API versioning" 55..59
  field ApiVersion
  via service-metadata
  via response-header
}
```

`via service-metadata` / `via response-header` are **not valid** — the FieldExposure grammar allows only `via query-select` or `via api-response`.

- Grammar: `packages/contract-verifier/src/parser-ohm/grammar.ts` → `FldExpChannel = kw<"query-select"> | kw<"api-response">`.

**Three distinct root causes here:**

1. **Mis-classification at enumerate.** "Version surfaced in service metadata / response headers" is not a field on a read path, so FieldExposure genuinely can't express it. The enumerate step still emitted it as a FieldExposure target (see the target hint in `00019`'s `user`: `FieldExposure: api-version-exposure — ApiVersion surfaced in service metadata and response headers`).

2. **The extract prompt has no closed-enum guardrail for `via`.** The system prompt (see "Prompt gap" below) *describes* the two channels and shows them in an example, but never states they are the ONLY legal values. With no "you may not invent other `via` values" rule, and a target hint literally naming "service metadata and response headers," the model wrote exactly that.

3. **Repair can't accept a reclassification.** On its FINAL repair attempt (`00024`) the model **correctly** reclassified the artifact to a valid `UnenforceableObligation`, with the rationale *"FieldExposure only supports query-select and api-response channels; service metadata and response-header exposure are not structurally encodable."* But the repair pipeline is keyed to fix the SAME (kind, identity) in place — it did not accept the kind change (FieldExposure → UnenforceableObligation), so the corrected fragment was discarded and the broken FieldExposure was dropped. **This is a real limitation worth fixing.** Look at the repair loop in `packages/contract-extractor/src/repair.ts` (how it matches/accepts a repaired fragment by kind+identity).

## Problem 6 — `Operation:POST /api/customers` dropped

**What happened.** The repaired operation (`00029`) contained a request body:

```
request {
  body {
    email: string format email
    name: string non-empty      ← invalid
  }
}
```

Parse error: `Line 7 … Expected ":"` — the parser, after `name: string`, doesn't recognize `non-empty` as a request-body modifier, treats it as the next field name, then expects `:` and hits `}`.

- Grammar: `packages/contract-verifier/src/parser-ohm/grammar.ts` → `OpFieldMod` allows `required / optional / references / constraint / compareNum / default / min / max / format / semantics` — but **not** a bare `non-empty`. The correct form is `name: string constraint non-empty`.
- Root cause: the model used an **Entity-field** attribute (`non-empty`) in a **request-body** context that needs `constraint non-empty`.

**Directions:** either (a) allow `non-empty` as an `OpFieldMod` alias for `constraint non-empty`, or (b) add a request-body example/rule to the prompt steering it to `constraint non-empty`.

## Prompt gap analysis (relevant to Problem 5)

The extract system prompt (`00019`'s `system`, ~1,400 lines) is structured as:

- **Faithfulness / Output / ArtifactKind catalog / `.tc` grammar essentials** (lines ~2–475) — rules, output shape, the kind list, and one `.tc` example per kind.
- **Syntax + identity + few-shot** (~476–560).
- **Per-kind extraction deep-dives** (~561–1378) — dedicated "when/how to extract THIS kind" sections for Operation, **Auth-requirement**, **Entity**, **Enum**, **Forbids**, **QueryRule**, **ForbiddenArtifact**, **NamedConstant**, **ArchitectureDecision**, **Authorization-rule**, error-envelope.
- **Naming conventions / Hard rules** (~1379–1407).

**Key finding:** every major kind gets a dedicated deep-dive section EXCEPT `FieldExposure`. FieldExposure appears only as (a) a one-line catalog entry and (b) a grammar example (`via query-select` / `via api-response`). The "`via` is a closed set of exactly two values" rule is stated **nowhere** — only implied by the example. That is why gpt-5.5 invented `via service-metadata`.

Source of the prompt: `packages/contract-extractor/src/prompt.ts` (`SYSTEM_PROMPT`), plus the shared `KIND_CAPABILITIES` sheet also in `prompt.ts`, and the enumerate prompt in `packages/contract-extractor/src/corpus-prompt.ts`.

# Additional root-cause findings (second investigation pass, 2026-07-02)

**F1 — repair rejected the correct answer three times (Problem 5).** ALL THREE repairParse
attempts (`00022`/`00023`/`00024`) returned the same, correct `UnenforceableObligation`
reclassification with a sound rationale ("FieldExposure only supports query-select and
api-response channels; …not structurally encodable"). The pass-0 acceptance filter in
`packages/contract-extractor/src/repair.ts` (`fragments?.find((f) => key(topLevelKind(f.kind),
f.identity) === k)`) requires the fragment to keep the original kind+identity, so the correct
answer was discarded three times (three wasted LLM calls) and the artifact was dropped. The
contradiction is internal: `FIX_SYSTEM_PROMPT` rule 3 explicitly instructs the model to emit an
`UnenforceableObligation` when a fix isn't expressible — the prompt authorizes exactly what the
acceptance code rejects. (Pass 1 already accepts the obligation fallback; pass 0 is the odd one
out.)

**F2 — repair passes 1 & 2 never parse-validate what they accept (Problem 6).**
`Operation:POST /api/customers` was not primarily a prompt problem: it was **born in repair
pass 1** (missing-artifact fix, dump `00029`), and pass 1 pushes fragments into the corpus
without ever calling the parser. Pass 0 (parse repair) runs BEFORE pass 1, so an artifact born
broken in pass 1 gets no repair chance — it flows straight to `validateMerged`, which
hard-drops it. Pass 2 (incomplete artifacts) has the same hole and is strictly riskier: it can
replace a parsing-but-incomplete artifact with an unparseable "fix", turning a working artifact
into a dropped one.

**F3 — pass 0's repair instruction is an impossible bind for inexpressible content.** The
issue text says "Fix ONLY the syntax … preserve every field, clause, and value it expressed".
When a clause is illegal in the kind's grammar (`via service-metadata`), that instruction
cannot be satisfied: the only truthful outs — reclassify to unenforceable-obligation (rejected
by the filter, F1) or drop the clause (forbidden by the instruction) — are both blocked.
Failure is guaranteed by construction.

**F4 — pattern audit: "know what you can produce / be told what you did wrong".** Only repair
pass 0 implements the full pattern (parser error fed back, fresh each bounded retry). Enumerate
gets no output validation and no retry; extract's fragments are never parse-checked at
generation time (a broken fragment travels the whole pipeline before anyone reacts); repair
passes 1/2 accept blindly (F2). The extract prompt's grammar section is a hand-written prose
copy of the real grammar and had drifted (the closed `via` set was stated nowhere — Problem 5).

# Solution plan

Design principles (agreed with the user):

1. **The model must know exactly what it can produce.** The prompt is the model's ONLY view of
   the grammar; anything unstated is a gap the model will fill on its own.
2. **Generated, not hand-copied.** Wherever the "what's legal" description has a
   machine-readable source (the ohm grammar), the prompt section must be derived from that
   source. Hand copies drift — that is precisely how the closed `via` set went missing.
3. **On failure, feed the exact error back and re-ask (bounded).** Make every stage work the
   way repair pass 0 already does.
4. **Fix the class, never the instance.** No per-keyword prompt patches; no grammar changes
   whose only purpose is to make bad output parse.

Explicitly NOT doing (and why):

- **No new `via` channels** (`service-metadata`, `response-header`): the verifier has no
  comparator that can check header/metadata exposure in code — the grammar must not promise
  what verify can't deliver. If header exposure becomes a real need it's a new-feature request
  (grammar + comparator), not part of this fix.
- **No bare `non-empty` alias in `OpFieldMod`**: it would create a second spelling of the same
  constraint (`constraint non-empty` is the canonical form everywhere, including entities) —
  poison for byte-stable regeneration.
- **No arbitrary kind reclassification in repair**: kind classification is owned upstream by
  enumerate + reconcile. Repair may fix within the kind or declare "inexpressible" (the one
  verdict every kind shares — Fix 7); letting it re-classify freely would create a second
  authority over classification and collide with the reconciled plan (e.g. a reclassification
  to `NamedConstant:ApiVersion` would have collided with the real, already-generated one).

Consequence to expect: Fixes 1–2 change `SYSTEM_PROMPT` (and the kind catalog shared with the
enumerate prompt), so `EXTRACT_PROMPT_FINGERPRINT` / `ENUMERATE_PROMPT_FINGERPRINT` change and
the `contract/{enumerate,extract}` caches bust — the next generate on changed specs re-runs
those stages once. Expected and correct. (The committed-manifest no-op is keyed on spec hashes
only, so a fully-unchanged repo still skips the pipeline entirely.)

## A. Models know what they can produce (prompts) — agent A

Owned files: `packages/contract-verifier/src/parser-ohm/` (new module + index export),
`packages/contract-extractor/src/prompt.ts`, new tests under `tests/`.

### Fix 1 — grammar-derived legality reference in the extract prompt

**What.** A new module in `@truecourse/contract-verifier` (next to the grammar it introspects,
e.g. `packages/contract-verifier/src/parser-ohm/keyword-sets.ts`) that derives, from the ohm
grammar source (`packages/contract-verifier/src/parser-ohm/grammar.ts`), every **closed keyword
set**: for each grammar rule whose alternatives begin with `kw<"…">` keyword literals (e.g.
`FldExpChannel`, `OpFieldMod`, `EntFieldMod`, `OpHeaderMod`, `FbkTrigger`, `OpEffectVerb`,
`EnumStmt`, …), the exact legal keywords plus a simplified rendering of each alternative's
argument shape. Rule selection is **mechanical** (any rule matching the criterion is included
automatically) — no hand-curated rule list, or the reference re-drifts.

`SYSTEM_PROMPT` in `packages/contract-extractor/src/prompt.ts` embeds the rendered reference as
a new section (near "# .tc grammar (essentials)") with an explicit framing rule: *these sets
are CLOSED — never use a keyword that is not listed; if what the spec says has no legal
encoding in the target kind, emit `unenforceable-obligation` instead*. The reference must be
compact (one line per rule/context) — it supplements, not replaces, the existing examples.

**Why.** Root cause of Problem 5 (invented `via service-metadata`) and the trigger of
Problem 6 (bare `non-empty` where only `constraint non-empty` is legal): the prompt never
stated the closed sets, only implied them via examples. Per design principle 2, the fix is
generation from the single source, not hand-written rules per incident.

**How (constraints).**
- Pure, deterministic function of the grammar source string (testable against a modified
  grammar string; stable output ordering).
- Computed at module load is fine (the grammar is parsed at load anyway); no build step
  required. `SYSTEM_PROMPT` stays a plain exported string.
- Acceptance: adding a keyword to a closed set in `grammar.ts` changes the generated prompt
  section with zero prompt edits; `query-select`/`api-response` appear as the only `via`
  channels; `constraint` appears among the op-field modifiers.
- Tests: determinism (two renders identical), sensitivity (feeding a grammar variant with an
  extra keyword changes the output), and presence of known sets — plus a snapshot of the
  rendered section.

### Fix 2 — every kind-catalog entry states its structural limits

**What.** `KIND_CAPABILITIES` (in `prompt.ts`, shared by the enumerate + extract prompts) is
the *semantic* half of "know what you can produce" — which concept maps to which kind, and what
each kind CANNOT express. Most entries already carry their limits ("NOT a field's existence",
"CANNOT express a comparison"); `FieldExposure`'s entry is missing its channel limit. Extend it:
exposure means a **query projection and/or an API response body** — a value surfaced via
response headers, service metadata, logs, or events is NOT a FieldExposure (if the spec pins
the value itself, that's a `NamedConstant`; otherwise it has no structural encoding). Audit the
other entries against the grammar's actual capabilities while there (catalog completeness, not
new prose styles).

**Why.** Problem 5 *started* at enumerate: "ApiVersion surfaced in service metadata and
response headers" was planned as a FieldExposure target, which the grammar genuinely cannot
express. The catalog is what enumerate picks kinds from; its entry must state the limit.

## B. Feedback loops in enumerate + extract — agent B

Owned files: `packages/contract-extractor/src/corpus-generate.ts`,
`packages/contract-extractor/src/corpus-prompt.ts`, `tests/contract-extractor/` tests for them.

### Fix 3 — enumerate output: closed-kind validation + one corrective re-ask

**What.** In `enumerateCached` (so every runner is covered, not just the spawn runner),
validate each returned target's `kind` against the closed kind list. The list is derived at
runtime by parsing `KIND_CAPABILITIES` lines (`/^- ([A-Za-z]+) —/`) — the catalog IS the
enumerate prompt's kind spec, so deriving from it keeps a single source. `UnenforceableObligation`
is NOT a valid enumerate kind (its catalog line says "NEVER enumerated as a target").
On invalid kinds: ONE corrective re-ask for that view listing the offending entries ("these
kinds are not in the catalog: … — re-emit the corrected JSON, choosing kinds only from the
catalog"); if still invalid after the re-ask, drop those targets (keep the valid ones) — never
fail the whole area over them. Only validated target lists are cached.

**Why.** Today an invented kind flows downstream unchecked ("extract honors the kind"). The
check is free and deterministic; the re-ask gives the model its mistake (design principle 3).

### Fix 4 — extract: parse-check fragments on arrival; retry misses WITH the parser error

**What.** In `generateAreaTargets` (`corpus-generate.ts`), parse-check each incoming fragment's
`tcSource` (`parserOhm.parseTcFile`, same oracle as repair) inside `emit()`:
- A fragment that parses → emitted as today.
- A fragment that fails → NOT counted as produced; record `coverageKey → parser error`. The
  target therefore stays in `missing()` and is re-requested by the EXISTING retry rounds — with
  the parser error attached to that target's line in the batch user prompt
  (`buildCorpusGenerateUserPrompt` gains optional per-target error hints, e.g. "your previous
  attempt failed to parse: <error, truncated>"; keep hints short).
- If a target's fragment still fails after the rounds are exhausted, **emit the last version
  anyway** so repair pass 0 can still attempt it downstream (the current recovery path is
  preserved — this fix only ADDS earlier, cheaper feedback; it must never reduce yield).
- The per-area extract cache continues to store the final fragments (now at most one
  unparseable per target, same as before).

**Why.** F4/F2: a broken fragment currently travels merge → normalize before repair sees it,
and the extract-stage retry rounds re-ask blind (the model repeats the same mistake). The
rounds machinery already exists; this feeds it the error.

### Fix 10 — retry a failed enumerate view once

**What.** In `enumerateCached`, on a view failure (timeout or any transport error), retry that
view ONCE (2 attempts total) before marking the area `failed`. Everything else (no caching on
failure, `enumerateFailures` surfacing, manifest exclusion) stays as is.

**Why.** Problems 1/2: enumerate is the only stage with a single-attempt policy — generate
retries via completeness rounds, repairParse retries 3×; that asymmetry is exactly why
`loyalty_tiers` recovered and the two areas didn't. gpt-5.5's successful enumerates ran p50 86s
/ max 248s against the 300s ceiling — the failures are marginal, and one retry recovers
variance cases (the timeout-scale knob, Fix 9, covers systematically slow models).

## C. Repair correctness — agent C

Owned files: `packages/contract-extractor/src/repair.ts`, `tests/contract-extractor/` tests
for it.

### Fixes 5+6 — passes 1 & 2 parse-gate their acceptance, with the pass-0 retry loop

**What.** Extract pass 0's bounded attempt loop (fresh parser error fed back each attempt;
`PARSE_REPAIR_ATTEMPTS` total) into a shared helper, and use it in all three passes. The
cheap-early/strong-last model escalation stays **pass-0-only** (mechanical syntax fixing);
passes 1/2 are generation work and run the strong `model` on every attempt:
- **Pass 1 (missing):** accept a fragment (target or obligation-fallback) only if its
  `tcSource` parses. On parse failure, re-attempt via the loop with the parser error appended
  to the issues. If it never parses, SKIP (leave the reference unresolved — a soft issue,
  strictly better than adding an artifact that `validateMerged` hard-drops).
- **Pass 2 (incomplete):** replace `artifact.winning` only with a parsing fix. On failure,
  retry via the loop; if it never parses, KEEP the previous winning (incomplete beats dropped)
  and log.
- Pass 0 keeps its existing behavior (it already is the loop).

**Why.** F2. Also fixes the ordering hole: artifacts born/replaced in passes 1/2 currently get
no parse check at all because pass 0 already ran.

### Fixes 7+8 — pass 0 accepts the "inexpressible" verdict; fix the impossible instruction

**What.**
- **Acceptance (7):** in pass 0, when no same-kind+identity fragment is returned, accept a
  PARSING `UnenforceableObligation` fragment as a deliberate downgrade: re-key the artifact
  (`artifact.kind`, `artifact.identity` — not just `winning`; the validator and writer key off
  the artifact fields). Collision guard: if the corpus already holds an artifact under the new
  `UnenforceableObligation:<identity>` key, fall back to today's behavior (tag
  `repairFailReason`, the validator drops it) — never worse than the status quo. Scope: the
  downgrade target is ONLY `UnenforceableObligation` (see "Explicitly NOT doing" — no arbitrary
  kind reclassification).
- **Instruction (8):** extend pass 0's issue text (and align `FIX_SYSTEM_PROMPT`): "…preserve
  every field, clause, and value it expressed. If a clause is NOT expressible in this kind's
  grammar at all, do not invent syntax — emit an `unenforceable-obligation` fragment (same
  identity) whose spec-text/rationale capture what could not be encoded."

**Why.** F1 + F3: the model returned the correct downgrade three times and the filter threw it
away; the instruction currently forbids every truthful output for inexpressible content.
Rule 3 of `FIX_SYSTEM_PROMPT` already authorizes the downgrade — this makes the acceptance code
and the instruction agree with it.

## D. Timeouts — agent D

Owned files: `packages/shared/src/llm/transport.ts`, `README.md` (env-var docs), tests for the
transport.

### Fix 9 — `TRUECOURSE_LLM_TIMEOUT_SCALE`

**What.** One env knob, read in `packages/shared/src/llm/transport.ts`: a float multiplier
(default 1; invalid/≤0 values fall back to 1) applied to `req.timeoutMs` in `cliTransport` and
to the deadline in `agentTransport`. Scaling at the transport is the single point every stage's
ceiling flows through (enumerate 300s, extract/repair/reconcile 600s, gapJudge 300s, and every
spec-scan stage) — per-stage relative ceilings are preserved. Document in the README next to
the other `TRUECOURSE_*` env vars. A gpt-5.5-via-proxy run would set `2`–`3`.

**Why.** Problems 1–3: the ceilings are fixed constants tuned for Claude tiers; a slow
model/proxy needs one knob, not a per-stage table (model IDs behind proxies are opaque, so
"model-aware" timeouts can't work).
